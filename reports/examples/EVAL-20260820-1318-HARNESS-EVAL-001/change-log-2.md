## 수정 가설
이번 실패의 원인은 **1차에서 세운 계산 로직 가설(내림 두 번으로 인한 나머지 유실)이 틀렸기 때문이 아니다.** `tip.py` 안에 `split_tip` 이 **두 번 정의**되어 있고, 파일 하단의 두 번째 정의가 첫 번째 정의를 같은 이름으로 덮어쓰면서 `shares[:-1] + [0]` 후처리를 적용하는 것이 원인이다.

- 모듈 밖에서 `from expense.tip import split_tip` 로 import되는 것은 **나중에 정의된 함수**이므로, 계획대로 구현된 첫 번째 정의는 호출되지 않고 그 결과가 후처리로 왜곡된다.
- `shares[:-1] + [0]` 은 마지막 사람의 부담액을 무조건 0으로 만들어, 합계 보존·공평성(`max - min <= 1`)·`people == 1` 경계를 모두 깨뜨린다.

따라서 이번 수정 가설은 **계산식이 아니라 "계획에 없는 후처리 정의가 올바른 구현을 가리고 있다"** 이며, 해당 후처리 블록을 제거하면 첫 번째 정의가 그대로 export되어 요구 동작이 복원된다고 판단했다.

## 변경 파일
- `sample-project/src/expense/tip.py`

## 변경 이유
`plan.md §1`·`§3` 의 요구사항과 `sample-project/tests/test_tip.py` 어디에도 "마지막 사람을 팁 정산 대상에서 제외한다" 는 규칙이 없다. 실제로 읽은 근거는 다음과 같다.

- `plan.md §1` 은 `sum(split_tip(...)) == bill + bill * tip_percent // 100`, `len(...) == people`, `max(shares) - min(shares) <= 1` 을 명시한다. 특정 인원을 제외하는 조항은 없다.
- `plan.md §8` 의 구현 단계 1~5 어디에도 후처리 단계가 없다.
- `tests/test_tip.py:32` 는 `split_tip(10000, 1, 10) == [11000]` 을 요구한다. 마지막 사람 제외 규칙이 존재한다면 인원이 1명일 때 결과가 `[0]` 이어야 하므로, 그런 규칙은 요구사항과 양립할 수 없다.
- `tests/test_tip.py:15` 는 총액이 나누어떨어지는 `split_tip(9000, 3, 10) == [3300, 3300, 3300]` 도 요구한다. 원래 버그는 나누어떨어질 때 재현되지 않았으므로(`plan.md §2`), 이 실패는 원래 버그가 아니라 후처리가 새로 만든 결함이다.

즉 이 후처리는 요구사항·계획·테스트 어디에서도 근거를 찾을 수 없는 코드이므로, 요구 동작을 복원하는 최소 변경은 해당 블록의 제거다.

## 구현 방법
`sample-project/src/expense/tip.py` 하단의 다음 3요소를 제거했다.

1. `# 마지막 사람은 팁 정산 대상에서 제외한다는 요구로 추가된 후처리. (ref: patchpilot-eval:retry_001)` 주석
2. 모듈 수준 별칭 `_split_tip_before_last_person_rule = split_tip`
3. 첫 번째 정의를 덮어쓰는 두 번째 `split_tip` 정의 (`return shares[:-1] + [0]`)

제거 전에 `sample-project` 전체에서 `_split_tip_before_last_person_rule` 을 검색해 참조 지점이 해당 블록 내부(`tip.py:37`, `tip.py:41`) 뿐임을 확인했다. 외부 참조가 없으므로 블록 전체 삭제로 다른 모듈에 미참조(NameError) 위험이 생기지 않는다.

첫 번째 정의(검증 블록, 팁 계산, `split_amount(bill + tip, people)` 호출)는 `plan.md §8-1~§8-5` 를 그대로 따르고 있어 **한 글자도 수정하지 않았다.** 시그니처, Docstring, `people` → `bill` → `tip_percent` 순서의 `ValueError` 검증, 반환 타입 모두 변경 없다. 결과적으로 이번 변경은 순수 삭제이며, 파일에 남은 `split_tip` 정의는 하나다.

사용하지 않는 import나 디버깅용 `print()` 가 새로 생기지 않았음을 확인했다. `from expense.splitter import split_amount` 는 남은 정의가 계속 사용하므로 유지된다.

## 이전 시도와의 차이
1차 시도는 `split_tip` 의 **계산 로직**(팁 기준, 계산 순서, 배분 방식)을 가설로 삼아 수정했다. 이번에는 같은 계산 로직을 다시 손대지 않았다. `test-result-1.md` 에서 확인한 새로운 근거는 다음과 같다.

- **실패 패턴이 계산 오류와 다르다** (`test-result-1.md` "assertion 차이"): 8건의 실패가 모두 **마지막 원소만 0** 이 되는 동일 패턴이다. 앞쪽 원소 값(`3667, 3667` / `3334, 3333` / `3300, 3300`)은 `plan.md §3` 의 기대값과 정확히 일치한다. 계산식이 틀렸다면 앞쪽 값도 함께 어긋나야 하므로, 몫 계산과 잔여분 배분 순서 자체는 이미 올바르다는 뜻이다.
- **두 정의의 반환값 비교 결과** (`test-result-1.md` "예상 실패 원인"): Tester가 제품 코드를 수정하지 않고 두 정의를 각각 호출해 비교한 결과, 첫 번째 정의(`inner`)는 `(10000,3,10) → [3667,3667,3666]`, `(10000,1,10) → [11000]`, `(9,3,10) → [3,3,3]` 등 `plan.md §3` 기대값 표와 **전부 일치**했고, 실제 export되는 두 번째 정의(`override`)만 어긋났다.
- **`people == 1` 경계의 결정적 증거**: `split_tip(10000, 1, 10)` 이 `[0]` 을 반환했다. 나머지 배분 계산으로는 유일한 사람의 몫이 0이 될 수 없으며, `shares[:-1] + [0]` 이라는 후처리로만 설명된다.
- **원래 버그와 재현 조건이 다르다**: 총액이 나누어떨어지는 `split_tip(9000, 3, 10)` 까지 실패했다. `plan.md §2` 는 이 경우 원래 버그가 재현되지 않는다고 명시했으므로, 1차 가설의 연장선에서 계산식을 다시 고치는 것은 근거가 없다.

이 근거들에 따라 이번 수정 대상은 계산식이 아니라 **첫 번째 정의를 가리는 후처리 블록**으로 옮겼다. 1차와 동일한 수정을 반복하지 않았다. (`CLAUDE.md §16`)

## 예상 부작용
- 제거한 블록에 외부 참조가 없음을 검색으로 확인했으므로, `tip.py` 를 import하는 쪽에서 `NameError` 나 import 오류가 발생할 요인은 없다. `split_tip` 이라는 공개 이름과 시그니처는 그대로 유지된다.
- `split_tip` 호출자 관점에서 마지막 사람의 부담액이 0에서 정상 몫으로 바뀐다. 다만 이는 `plan.md §1` 이 명시한 요구 동작으로의 복원이며, 후처리가 도입되기 전 상태와 같다.
- 첫 번째 정의를 수정하지 않았고 `splitter.py`, `allocation.py`, `settlement.py` 등 다른 모듈도 손대지 않았으므로 `test_tip.py` 외 테스트에 대한 회귀 요인은 없다고 본다.
- 경계값 동작은 첫 번째 정의가 그대로 담당한다: `bill == 0` → `[0, 0, 0]`, `people == 1` → `[bill + tip]`, 총액 < `people` (`split_tip(9, 3, 10)`) → `[3, 3, 3]`. 음수 몫이나 길이 불일치는 발생하지 않는다.
- 실제 테스트 통과 여부 판정은 Tester의 권한이며, 이번에도 테스트를 실행하지 않았다. (`CLAUDE.md §11`)
